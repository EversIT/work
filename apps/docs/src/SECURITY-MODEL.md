# Security model

How work protects itself, why, and where it still falls short. Read this before you change anything that
touches authentication, authorization, files, outgoing requests or third parties. To report a
vulnerability see [SECURITY.md](https://github.com/EversIT/work/blob/main/SECURITY.md).

## Design rules

Reviewers hold changes to these:

1. **Secrets come from the environment only.** No defaults, no committed credentials; startup fails when one is
   missing or weak (`apps/docs/src/CONFIGURATION.md`).
2. **Every protected handler takes an `AuthUser`** and checks the caller's role on the resource's project in
   `security/authz.rs` before touching data. Non-members get `404`, so ids cannot be probed. Roles are read
   from the database on every call, never from a token.
3. **Request bodies are explicit structs.** Nothing is deserialized straight into a database row, so a client
   can never set a role, an owner or a password hash.
4. **All SQL uses bound parameters.** Sort and filter columns come from closed enums or allow-lists.
5. **Short-lived access tokens in memory; the refresh token is an `HttpOnly; SameSite=Strict` cookie**, rotated
   on use, with reuse detection.
6. **The backend is never published.** It is reached only through the frontend's `/api/v1` proxy.
7. **Untrusted content is rendered by React from a validated structure, never as HTML.** Uploaded files are
   sniffed, served as attachments with a sandboxing policy, and only through the authenticated API.
8. **Outgoing requests go through the SSRF guard** and never follow redirects.
9. **Every administrator action is written to an audit log**, and admin endpoints answer `404` to everybody else.

## Not verified

- Dependency vulnerabilities are checked in CI (`cargo audit`, `npm audit`); results depend on the advisory database at that time.
- SSO, SAML, S3 and Azure were exercised against local stand-ins, not the real services. The SAML library is a pre-release crate without an independent audit.
- The automation engine was written against the behaviour of the project this one replaces; it re-implements it with owner-rights checks, a depth limit against loops and non-evaluating placeholders.

## Known residual risks

- Without SMTP, e-mail confirmation is off and registration reveals whether an e-mail exists (`409`).
- Lock-out can be used to lock a known account out for a while (denial of service against one user). The owner is told by mail, a password reset lifts the lock, and the per-IP limit bounds how many accounts one source can lock.
- Signing in through SSO, OpenID Connect or SAML does not ask for the local second factor (the provider authenticates the person). A passkey counts as two factors on its own.
- Passkeys: only ES256 credentials, and attestation is not verified ("none"), so the authenticator's make and model are not checked.
- Live editing and notifications fan out in process: with several backend instances, route the editors of one card to the same instance (the saved content is shared through the database either way). Saved content is whatever the last saving editor sent; two editors saving in the same instant can briefly disagree until the next edit.
- SAML relies on a pre-release library without an independent audit, and on `SameSite=None` for the response cookie (so SAML needs https). Over plain `http://localhost` SAML does not work. Single logout and encrypted assertions are not supported.
- Replay protection for SAML assertions is per instance (the one-time `state` row, which is shared, is the primary guard).
- `style-src` still allows `'unsafe-inline'` (the UI kit sets style attributes). Inline styles cannot run script.
- Style attributes aside, the interface sets no colour inline; the accent colour is validated as `#RRGGBB` before it reaches a style.
- The default rate limiter is per instance; set `WORK_RATE_LIMIT_BACKEND=postgres` when running several.
- Dependency audits (`cargo audit`, `npm audit`) run in CI; results depend on the advisory database at that time.
